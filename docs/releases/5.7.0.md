# Gantry 5.7.0 feature release

Framework SemVer: **5.7.0**. Calendar identity: **2026.11.01.003**.
Release tag: `v2026.11.01.003`. The owner's real-content proving-site acceptance
and private backup restoration passed before publication. The published
5.6.6 maintenance release and separate Gantry 6 alpha stay intact.

## Feature scope

This release takes PR #11's two feature commits onto the maintained Gantry 5.6.6
line. It includes every item below on PHP 8.4, without the Gantry 6 dependency or
API migration:

- **Upgrade assistant:** selected-outline local compatibility preflight, explicitly
  acknowledged private YAML snapshots, read-only restore previews, stale-state
  refusal and guarded restoration with compensating file recovery. A snapshot can
  contain private content; it does not include a CMS database, media or other outlines.
- **Layout editing:** exact section-blueprint Styles controls save independently
  while preserving the unsaved Layout draft and unapplied section inputs. A separate
  saved-site preview uses 390, 768 and 1280 CSS-pixel viewports and normal assignments.
- **Design packs:** reviewed visual palette, typography, supported installed particle
  placements and bounded custom bitmaps with full supplied licenses/notices. Import
  creates a new unassigned native outline and preserves existing content/assignments.
- **Client mode:** default-off approved literal text editing for existing native
  page-editing users. Settings administrators explicitly approve dedicated instances;
  native tokens, policy/layout revisions and stale-state refusal protect saves.
  Other Gantry settings and layouts remain outside the restricted interface.
- **Accessibility/navigation:** keyboard and focus navigation, current-level Tab
  handling, submenu-first Escape, reduced motion, off-canvas transition/ARIA state,
  observer cleanup, cancelable touch handling, breakpoints and back-to-top scrolling.
  These changes do not establish complete accessibility or physical-device acceptance.

The nullable rewriter, legacy SCSS interpolation, native Grav error authority,
Joomla/Grav Font Awesome admission and full license/notice packaging from 5.6.6
remain included. Existing documented icon-cache behavior and Grav 1.7 host/vendor
deprecations remain compatibility limits rather than silently claimed fixes.

Read [upgrade snapshots](../upgrade-assistant.md), [editor tools](../editor-tools.md),
[design packs](../design-packs.md), [client editing](../client-editing.md) and
[frontend behavior](../frontend-accessibility.md) for the supported scope.

## Runtime and package boundaries

The framework dependency range remains **PHP >=8.1.0 <8.5.0**. Package pins in all
Composer manifests/locks are unchanged from 5.6.6. Twig/Symfony/Toolbox modernization,
WordPress Timber 2, Grav 2/Admin2 and PHP 8.5 belong to the separate Gantry 6 line.
Earlier PHP versions retain their existing declaration/CI scope; PHP 8.4 is this
feature release's native acceptance target.

Only these three framework packages are release assets:

- `joomla-pkg_gantry5_v5.7.0.zip`
- `wordpress-pkg_gantry5_v5.7.0.zip`
- `grav-pkg_gantry5_v5.7.0.zip`

PR #11 changes shared framework/Nucleus/frontend assets, not the Helium or Hydrogen
source trees. Official default themes therefore keep their actual **5.6.4** identity.
Do not distribute the normal builder's relabeled theme ZIPs as this release.
The proving theme is the existing `g5_jmafia` with its real site configuration and
content. A successful Helium fixture alone cannot satisfy that acceptance gate.
No installed update channel is redirected by this release.

## Required acceptance before publication

1. Preserve a private file/database backup of the proving site and verify its
   restoration in an owned isolated copy. Bind the served document root, actual
   PHP 8.4 SAPI, Joomla version, Gantry framework, existing theme and assignments.
   Keep backups, configuration, cookies/tokens and content outside source/GitHub.
2. Build the complete tracked source with existing pinned dependencies and bundled
   static assets. Run the project's real PHP 8.4, frontend and native installer
   suites, including the snapshot, design-pack and client-boundary checks.
3. Install the exact reviewed Joomla framework package on the authorized proving
   site. Preserve the existing theme, its real content, menus and assignments.
   Check actual public/admin requests, saved styles/SCSS and served CSS, runtime
   identity and bounded logs, using existing authorized native actors.
4. Run the same feature acceptance against that real site: snapshot/preview/restore
   and stale refusal; independent section Styles preserving a dirty Layout draft;
   saved-site preview widths and real pages; pack preview/import as an unassigned
   outline with assignments/content preserved; default-off client admission and
   guarded approved-text round trip; menu keyboard/focus/reduced-motion behavior.
   Keep any private snapshots/downloads local and restore intentional test changes.
5. Review the actual results and rollback status. A failure holds publication until
   fixed and rerun. Named fixture results or an HTTP 200 alone do not pass this gate.
   Only after the real-site run passes may the source/tag/packages become public.

## Completed acceptance and limits

The proving site used Joomla **6.2.0**, actual PHP **8.4.26** and the unchanged
`g5_jmafia` theme with its real content. A private file/database backup was restored
in isolation: all **76 tables** and logical content matched, with ordinary session
activity and a storage-level index checksum difference resolved by logical comparison.

Actual-site HTTP phases passed: assigned-outline preflight/private snapshot and
refusals **30 checks / 16 requests**; native design-pack import and owned-outline
guarded restoration **32 / 16**; ordinary editor login/default-off denial **5 / 4**;
restricted approved text saves, literal rendering, stale/extra-field/CSRF/refusal
and revocation **31 / 23**; native test-outline deletion **7 / 2**. Browser phases
passed **47** real-page/menu/preview checks at 390/768/1280 pixels and **12** Layout
checks, including exact unsaved-draft preservation during independent section saves.
The browser harness awaited native Apply completion; preparation corrections did
not require product changes. Native Joomla denial wrappers can return HTTP 200;
checks verified protected content was absent and private state unchanged.

Final independent checks passed **19 preservation**, **10 cleanup** and **5 account,
profile and credential comparisons**, with no temporary-ID allowances. All **137**
stored articles, public menu/module assignments, actual configuration, theme source
and existing authority remain preserved. The original account's password hash and
profile matched the backup; only its normal last-visit timestamp differed. The
owner-approved temporary editor/group, its sessions/grants, the unassigned test
outline and its generated files were removed. Native installer registration/admin
menu metadata changed as expected; one stale derived layout index regenerated and
was independently verified against the unchanged source layout.

On isolated PHP **8.4.27**, existing suites passed: nullable **9 cases / 71 checks**,
catalogues **8 / 20**, snapshots **38**, design packs **43**, client editing **21**,
and **10** Composer platform checks. The frontend fixture passed **36** browser
checks. Native WordPress 7.1.4 phases passed core **54**, snapshots **32** and
pack/Layout/client **30** checks; classic Grav 1.7.53.8/Admin 1.10.60 passed core
**26**, snapshots **23**, design packs **30**, client **29** and final Hydrogen
checks **9**. Reused phase setup overlaps; these counts are not a distinct-case sum.

The proving site's existing error reporting remained **22527**, which excludes PHP
E_DEPRECATED; no visible PHP errors or matching new site-log diagnostics were seen.
This is not complete real-site E_ALL coverage. Isolated native phases ran E_ALL;
WordPress logged no PHP diagnostics, while Grav retained **316 host/core deprecation
lines** outside Gantry. Broader third-party, older-CMS, physical-device and full
accessibility acceptance remain outside these checks. Snapshot rollback covers
selected-outline YAML rather than the database, media or a full framework downgrade.

## Installation and rollback

Keep the previously installed framework and a tested private file/database restore
point. Use each CMS's native install workflow (or Grav's normal file-install path).
Do not replace themes, move assignments or run a dependency migration as part of
this framework feature update. Feature-created outlines are unassigned by design;
private YAML snapshot rollback is narrower than a full site or framework rollback.
Restore the tested site file/database state if the proving run fails; record the
actual deployed state rather than assuming a ZIP install or rollback succeeded.
